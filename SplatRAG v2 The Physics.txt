SplatRAG v2: The Physics-Native Memory Substrate1. Introduction: The Case for Dynamic Semantic MatterThe prevailing paradigm of artificial memory—the vector database—is fundamentally static. It treats information as dead weight, immutable vectors suspended in a high-dimensional void, retrieved only by the crude metric of cosine similarity. This architecture, while functional for static retrieval-augmented generation (RAG), fails to capture the fluid, evolving nature of intelligence. Thoughts are not static points; they are dynamic entities that attract, repel, cluster, and decay. They possess "mass" (importance), "velocity" (relevance over time), and "charge" (sentiment or truth value).SplatRAG v2 proposes a radical shift: the transduction of multimodal digital existence into a Physics-Native Memory Substrate. By ingesting the totality of a user's digital footprint—every chat, keystroke, and screen pixel—and instantiating them as 3D Gaussian primitives, we transform memory into a living field. This substrate evolves under true N-body physics, where "truth" is a gravity well and "hallucination" is repelled by negative mass. Retrieval is no longer a database query; it is a rendering process, a Monte Carlo sampling of the photon flux emitted by the memory field.This report provides an exhaustive technical analysis of the components required to build this system using the technology landscape of 2020–2025. It dissects the ingestion sensors necessary to capture the ephemeral web, the differentiable transduction layers that turn text into geometry, the cryptographic protocols to ensure provenance, and the simulation architectures that allow billion-particle semantic fields to evolve in real-time.2. The Sensorium: Universal Real-Time IngestionThe efficacy of any memory system is strictly bounded by its intake. A perfect memory substrate requires "God-mode" observability—a complete, low-latency intercept of the user's cognitive output and digital intake. This layer, the Sensorium, must operate across the fragmented ecosystem of proprietary web interfaces, local inference engines, and development environments.2.1 The Ephemeral Web: Intercepting the Chat InterfaceThe primary interface for modern intelligence interaction is the web browser, specifically the chat interfaces of Grok, Claude, ChatGPT, Gemini, and Perplexity. These platforms often serve as "walled gardens," with APIs that lag behind their web capabilities or lack the granular metadata (e.g., chain-of-thought tokens) available in the UI. To build a permanent memory, we must capture the raw render stream of these interfaces with near-zero latency (<50 ms).2.1.1 DOM Mutation and Network Interception ArchitecturesThe naive approach to browser capture involves periodic polling of the Document Object Model (DOM), but this introduces unacceptable latency and CPU overhead. Modern Single Page Applications (SPAs) like ChatGPT and Claude utilize the Shadow DOM and React fiber trees, making robust selection difficult.A superior architectural pattern, observed in high-performance extensions like ChatGPT Exporter 1 and Save Grok Chat 3, utilizes a combination of MutationObserver for structural changes and NetworkObserver (hooking window.fetch and XMLHttpRequest) for data payloads.By injecting a content script that proxies the native fetch method, the SplatRAG ingestion layer can intercept the streaming JSON chunks returned by the LLM providers before they are even parsed by the browser's rendering engine. This technique, employed by advanced exporters, allows for the capture of "invisible" metadata—server-side timestamps, model version hashes, and "thinking" traces that might be visually hidden in the UI but present in the payload.For Grok.com and X.com, specifically, the challenge is obfuscation. As noted in the Save Grok Chat research 3, X.com frequently randomizes CSS class names to thwart scrapers. A robust ingestion strategy relies on heuristic anchors—searching for stable ARIA labels or specific SVG icons (like the "Copy" button or "Regenerate" icon) to locate the text container relative to the message block. The ingestion script acts as a daemon, normalizing these disparate DOM structures into a unified "ThoughtEvent" schema containing the prompt, the response, the model ID, and the timestamp.2.1.2 Unified Chat Aggregation FrameworksRather than maintaining fragile scripts for each provider, a "Meta-Interface" approach offers greater stability. Tools like Sider 4 and ChatMultiAI 5 function as browser sidebars that wrap multiple LLM providers. By analyzing the architecture of Sider, we observe it maintains simultaneous sessions with ChatGPT, Claude, and Gemini.For SplatRAG v2, the optimal integration path is to fork an open-source base like ChatGPT Exporter 1 or utilize the sidebar injection technique of ChatMultiAI. The extension serves as a "Man-in-the-Browser" (MITB), not for malicious intent, but for memory persistence. It establishes a persistent WebSocket connection to the local SplatRAG daemon (running via Screenpipe or similar). As tokens stream in from the LLM provider, they are immediately forwarded to the local daemon. This "dual-write" architecture ensures that even if the browser tab crashes or the user deletes the chat history on the server, the local physics-native memory retains the interaction.2.2 The Subconscious Loop: Local Inference HooksLocal Large Language Models (LLMs) running via Ollama, LMStudio, or vLLM represent the "subconscious" of the SplatRAG system—private, uncensored, and high-speed. Unlike web interfaces, these systems offer direct access to the inference generation loop.2.2.1 Middleware Proxy InjectionThe most robust method for intercepting local traffic is the "LLM Gateway" pattern. LiteLLM 6 has emerged as the industry standard for this middleware layer. Written in Python, LiteLLM acts as a transparent proxy that translates between the OpenAI API format and various backends (Ollama, HuggingFace, Bedrock).For SplatRAG, we configure LiteLLM to sit between the user's frontend (e.g., OpenWebUI, SillyTavern) and the model runner. The critical modification required is deep inspection of the streaming response. Standard logging in LiteLLM 6 captures the final output, but for physics-native memory, we want the stream. Each token is a particle.We implement a custom callback in LiteLLM's success_callback hook.7 This callback taps into the generator object yielding the tokens. As each chunk arrives, it is timestamped with microsecond precision and pushed to the SplatRAG ingestion queue. This granular timing allows the physics engine to reconstruct the "velocity" of the thought—did the model hesitate? Did it burst forth with high confidence? These temporal dynamics map directly to the initial velocity vectors of the spawned 3D Gaussians.2.2.2 Direct Inference Engine HooksFor ultra-low latency (<2ms), we can bypass the HTTP layer entirely by hooking the inference engine's stdout or internal event bus. Ollama 9 exposes an HTTP server, but internally it wraps llama.cpp. Research indicates that ollama serve utilizes WebSockets for chat streaming.10 By connecting a lightweight generic WebSocket client to the Ollama port, the SplatRAG daemon can subscribe to the token events directly.Similarly, frontends like SillyTavern and OpenWebUI are rich sources of metadata. They manage the "World Info" and "Character Cards" that provide context. Capturing the raw text is insufficient; we must capture the active context—the specific character definition and system prompt active at the moment of generation. The OpenWebUI "Pipelines" feature allows injecting a Python script that exports the full context window alongside the generated text.12 This context vector becomes the "positional embedding" that initializes the Gaussians in the correct semantic cluster.2.3 The Logic Substrate: IDE and Code TelemetryCode is a structured form of thought, characterized by strict dependencies and logical flow. Capturing the "thought process" of a developer requires recording the evolution of the codebase, not just the final commit.2.3.1 Keystroke Dynamics and LSP EventsThe Visual Studio Code (VSCode) Extension API 13 provides the necessary hooks for this granular capture. We move beyond simple file watchers to semantic listeners.Keystroke Logging: Extensions like Log Ninja 14 and ActivityWatch (aw-watcher-vscode) 15 demonstrate the use of workspace.onDidChangeTextDocument. This event fires on every edit, providing the content changes (deltas). SplatRAG v2 treats every keystroke as a potential particle, but to prevent noise, it aggregates these into "bursts" of activity. A pause in typing of >500ms triggers the solidification of a "Code Block" Gaussian.LSP Diagnostics as Valence Signals: The Language Server Protocol (LSP) emits diagnostic information—errors, warnings, and hints.16 This is critical for the "Physics-Native" aspect. A code block that generates an LSP Error (red squiggle) is instantiated with Negative Valence. In the physics simulation, this negative valence creates a repulsive force. When the user later queries for "working sort algorithms," the retrieval ray will naturally be deflected away from the error-prone code implementation due to the repulsive field generated by the negative mass of the error particles.2.3.2 Security Considerations in TelemetryThe existence of malware masquerading as VSCode extensions, such as the "GlassWorm" campaign 17, highlights the risks of "log every keystroke" functionality. Legitimate security research 18 emphasizes that user-space keyloggers must be strictly sandboxed. SplatRAG v2 mitigates this by keeping all data local. The capture extension does not transmit to the cloud; it writes to a local named pipe or WebSocket secured by a strictly local interface (loopback only), managed by the Screenpipe daemon. This ensures that the high-fidelity capture of the user's coding stream remains a private memory asset, not a data exfiltration vulnerability.2.4 The Holoflux: Cross-Platform Unification via ScreenpipeTo fuse the disparate streams of browser chats, local LLM tokens, and IDE events into a coherent timeline, a system-level unification framework is required.Screenpipe 20 identifies as the paramount open-source solution for this (2024-2025). Written in Rust, it provides 24/7 screen and audio capture with efficient local storage.The "Pipe" Architecture: Screenpipe's plugin system ("pipes") allows for custom logic to be executed on the capture stream. The SplatRAG daemon is implemented as a Screenpipe Pipe.Multimodal Fusion: Screenpipe provides a continuous video buffer and an audio transcription stream (via embedded Whisper). The SplatRAG pipe subscribes to these streams. When a "Chat Event" is received from the Browser Extension, the pipe correlates it with the visual state of the screen (e.g., the diagram the user was looking at in another window) and the audio context (e.g., the user muttering "this isn't working" into the mic).Optical Character Recognition (OCR): Screenpipe's integrated OCR 23 acts as a fallback. If the Browser Extension fails (e.g., due to a DOM update), the OCR stream provides a lower-fidelity but reliable text stream, ensuring no thought is ever lost.ComponentTarget SourceCapture MethodLatencyIntegration ToolBrowserGrok, Claude, ChatGPTNetwork Intercept (XHR/Fetch)< 5 msChatGPT Exporter (Fork)Local LLMOllama, vLLMProxy Middleware< 10 msLiteLLM + Custom CallbackIDEVSCode, JetBrainsLSP & Document Listeners< 10 msActivityWatch (Fork)OS/ScreenWindows/Mac/LinuxFrame Buffer & Accessibility APIReal-timeScreenpipe3. Semantic-to-Spatial Transduction: The Geometry of ThoughtOnce captured, the raw data must be transmuted into the fundamental primitive of SplatRAG: the 3D Gaussian. This process, Semantic-to-Spatial Transduction, maps high-dimensional semantic embeddings into the geometric attributes of a splat: Position ($\mu$), Covariance ($\Sigma$), Color/Spherical Harmonics ($c$), and Opacity ($\alpha$).3.1 Differentiable Feature EmbeddingTraditional 3D Gaussian Splatting (3DGS) optimizes purely for photometric loss (RGB colors). For a memory substrate, we must optimize for semantic density. The works on Feature 3DGS and LangSplat 24 provide the theoretical foundation.Instead of just RGB colors, each Gaussian carries a feature vector $f$. Since storing a 512-dimensional CLIP vector for every keystroke is prohibitive ($10^{11}$ vectors would consume petabytes), we employ Decoupled Feature 3DGS.26Quantized Codebooks: We learn a compact codebook of semantic concepts. A specific Gaussian stores an index into this codebook (or a linear combination of a few bases), drastically reducing storage.Dimensionality Reduction: An autoencoder compresses the 512-D embedding into a lower-dimensional manifold (e.g., 16 dimensions) that is stored on the splat. During retrieval, a lightweight MLP decoder reconstructs the full semantic vector.3.2 The Mapping FunctionThe function $\Phi: \text{Token} \to \text{Gaussian}$ is a learned, differentiable map.Position ($\mu$): Initialized via a streaming dimensionality reduction (like UMAP or parametric t-SNE) applied to the text embedding. This places semantically similar concepts (e.g., "Python" and "Flask") in physical proximity within the 3D memory field.Covariance ($\Sigma$): Mapped from the uncertainty or generality of the concept. A specific fact (e.g., "The API key is sk-123") maps to a tight, small-variance sphere. A broad concept (e.g., "Philosophy of AI") maps to a large, diffuse, anisotropic ellipsoid. This allows the rendering camera to see "forests" of general knowledge and "trees" of specific facts depending on the zoom level.Spherical Harmonics (SH): The "color" of the thought is used for visual debugging and sentiment analysis. We can map sentiment (positive/negative) to the red/blue color axis, allowing the user to visually inspect the "emotional temperature" of their memory field.3.3 Gradient Flow from Text to GeometryThe transduction is not static; it is optimized via Score Distillation Sampling (SDS).27 Just as text-to-3D generation models use diffusion priors to sculpt a 3D asset, SplatRAG uses the incoming stream of "future text" to refine the positions of "past text." If the user clarifies a previous statement, the gradients from the new statement flow back to the old Gaussians, adjusting their position or covariance to better align with the updated understanding. This is a form of retroactive interference implemented as gradient descent on the memory field.4. The Physics Engine: N-Body Evolution and Negative MassThis is the defining innovation of SplatRAG v2. The memory field is not a static index; it is a dynamic simulation. Gaussians are particles that exert forces on one another, self-organizing into clusters of knowledge without manual curation.4.1 Learned Force Laws in Semantic SpaceStandard gravitational dynamics ($F \propto 1/r^2$) are insufficient for semantic organization. We require Learned Force Laws 29 modeled via Neural Ordinary Differential Equations (Neural ODEs).The force $F_{ij}$ between memory $i$ and memory $j$ is given by a learned function $F_\theta(z_i, z_j, r_{ij})$, where $z$ represents the semantic features.Semantic Attraction: If $\text{sim}(z_i, z_j)$ is high (concepts are related), an attractive force pulls them together. Over time, this causes the memory of a "Project A" chat to physically merge with the memory of "Project A" code files, forming a dense cluster.Temporal Decay (Friction): Particles experience a drag force proportional to their age. Unaccessed memories slowly drift toward the periphery or "sink" to a lower energy state (lower opacity), implementing a natural forgetting curve.4.2 Negative Mass and Repulsive DynamicsSplatRAG v2 integrates the exotic physics of Negative Mass 32 to solve the problem of hallucinations and errors.The Negative Mass Particle: When a user marks a generation as "Hallucination" or a code block as "Buggy," the system inverts the mass sign of the corresponding Gaussians ($m \to -m$).Interaction Rules:Positive-Positive: Attract (Gravity).Negative-Positive: Repel.The "Exclusion Zone": A negative mass memory physically pushes away all positive mass memories. If the system hallucinates a fake API endpoint, tagging it as negative mass ensures that no future "correct" API documentation Gaussians can exist in that exact semantic location. The error creates a void in the memory field, forcing the retrieval path to route around it.Stability: Simulating negative mass in N-body systems can lead to runaway acceleration (the "runaway motion" paradox where a positive and negative particle chase each other infinitely). To prevent this, we employ Smoothed Particle Hydrodynamics (SPH) kernels 32 with a friction term that dampens the velocity of negative-positive pairs, effectively "freezing" the error in place as a static repulsive bollard.4.3 High-Performance Simulation: Taichi and WarpSimulating $10^9$ particles in real-time requires massive GPU parallelism.PhysGaussian (Taichi): The PhysGaussian framework 36 demonstrates the "What You See Is What You Simulate" (WS2) paradigm. It uses the Gaussian kernels themselves as the simulation particles (MPM). We adopt this approach, implementing the N-body kernel in Taichi (a Python-embedded DSL that compiles to CUDA).NVIDIA Warp: Alternatively, NVIDIA Warp 39 offers a Python interface for writing differentiable physics kernels. Warp is particularly suited for the learning loop—backpropagating retrieval errors to update the force laws.5. The Memory Field: Storage, Compression, and StreamingStoring a permanent record of digital life generates a massive dataset. Efficient storage and streaming are critical.5.1 Optimization-Free Compression (FCGS)We cannot afford to run optimization (gradient descent) to compress the field every time a new memory is added. We rely on Fast Compression of 3DGS (FCGS) 41, presented at ICLR 2025.Method: FCGS uses a feed-forward neural network to compress Gaussian attributes into a bitstream without per-scene optimization. It employs a multi-path entropy module to balance size and fidelity.Performance: It reduces the memory footprint by >20x compared to raw FP16 storage, allowing terabytes of raw "thought" to fit on a consumer SSD.5.2 The SPZ Format and Web StreamingFor visualization and web-based retrieval, we utilize the .spz format 42, recently standardized by Niantic and the Khronos Group. This format is the glTF equivalent for Splats, supporting quantization and streaming.StreamingGS: To handle fields larger than GPU memory, we implement StreamingGS.45 This technique organizes the Gaussians into a hierarchical Level-of-Detail (LOD) octree. When the retrieval camera moves through the memory field, only the local leaf nodes (the specific memories being accessed) are streamed into VRAM, while distant memories are rendered as low-fidelity "clouds."5.3 Incremental Learning: Avoiding Catastrophic ForgettingAdding new memories must not destroy old ones. Incremental Gaussian Splatting (I-GS) 46 and CL-Splats 47 provide the methodology.Replay Buffers: We maintain a small buffer of "exemplar" past memories. When optimizing the field for new data, we enforce a constraint that the rendering of these past exemplars must not change.Adaptive Densification: New Gaussians are spawned only where the current field density is insufficient to represent the new information (high "error" in the transduction loss), ensuring that we simply add to the field rather than overwriting it.6. Rendering as Retrieval: The Monte Carlo EyeIn SplatRAG, "searching" is "seeing." Retrieval is achieved by placing a virtual camera in the semantic space and rendering the view.6.1 The Query as Camera PoseA search query ("What was the API key for Grok?") is embedded via CLIP to a coordinate $q \in \mathbb{R}^3$. The virtual camera is placed at $q$.Focal Length: The specificity of the query determines the field of view. A broad query has a wide FOV (seeing the whole cluster); a specific query has a narrow FOV.6.2 Monte Carlo Sampling and Probabilistic RetrievalStandard rasterization is deterministic. For retrieval, we need to capture the uncertainty and diversity of memory. We employ Monte Carlo Sampling.48Ray Casting: Instead of rasterizing pixels to a screen, we cast rays into the field. Each ray interacts with the Gaussians it intersects based on their opacity ($\alpha$) and probability density.The Integral: The value returned by the ray is the integral of the semantic features along its path. $\text{Result} = \int_{0}^{\infty} T(t) \sigma(t) c(t) dt$, where $c(t)$ is the semantic text information.Interpretation: The paper "3D Gaussian Splatting as Markov Chain Monte Carlo" 49 allows us to interpret the resulting pixel colors (features) as samples from the posterior distribution of the memory. If the rendered image is "blurry" (high variance in samples), the system reports low confidence.7. Cryptography and Provenance: The Immutable ChainTo trust a permanent memory, we must ensure it hasn't been tampered with and that we can control access to it.7.1 C2PA for Thought ChainsWe adapt the C2PA (Coalition for Content Provenance and Authenticity) standard 50 for memory.Signed Gaussians: At the moment of ingestion (in Screenpipe/Extension), the raw data is hashed and signed with the user's private key. This signature is attached to the generated Gaussian as a metadata attribute.Verification: During retrieval, the renderer checks the signature chain. If a memory block has been modified (e.g., by a malicious plugin), the signature verification fails, and the renderer refuses to include it in the output (or renders it as a "corrupted" black void).7.2 Steganography and Access ControlPublic fields (shared team memory) may contain private thoughts. We use SecureGS 53 and GS-Hider 55 for steganographic encryption.Hidden Attributes: Sensitive text is encrypted and embedded into the high-frequency spherical harmonics coefficients of the Gaussians. To a viewer without the key, the Splat looks like a generic gray blob.Key-Based Rendering: When the user presents the correct private key, the renderer's shader decodes the high-frequency coefficients, revealing the true color/text of the memory. This allows for "Selective Disclosure" within a single unified memory field.8.
